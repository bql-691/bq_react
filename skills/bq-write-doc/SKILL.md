# 撰写一篇正式文档

只写 `doc/项目文档/` 下的正式文档。撰写说明里的 `doc/功能模块`、`doc/基础应用`、`doc/项目架构.md`，在本仓库分别是 `doc/项目文档/功能模块`、`doc/项目文档/基础应用`、`doc/项目文档/项目架构.md`。

不改 `src/`。不改 `rules/`、`skills/`。不把 `doc/基础知识/` 的内容写进正式文档。不新建撰写说明里没有的章节。

## 先确定这一篇是哪一种

用户没有同时写出文档种类和文件路径时，停止并询问。下表四种只选一种：

| 种类             | 依据                                             | 路径                                                   |
| ---------------- | ------------------------------------------------ | ------------------------------------------------------ |
| 功能模块主文档   | `doc/项目文档/功能模块/*功能模块文档撰写说明.md` | `doc/项目文档/功能模块/<模块名>/<模块名>(<目录名>).md` |
| 功能模块业务文档 | 同一篇撰写说明的「业务文档写什么」               | `doc/项目文档/功能模块/<模块名>/<业务名>.md`           |
| 基础应用         | `doc/项目文档/基础应用/*基础应用文档撰写说明.md` | `doc/项目文档/基础应用/<中文名>(<目录名>).md`          |
| 项目架构         | `doc/项目文档/*项目架构文档撰写说明.md`          | `doc/项目文档/项目架构.md`                             |

先读 `doc/项目文档/*撰写总则.md`，再只读上表中这一篇的撰写说明。

功能模块业务文档必须已有主文档。主文档不存在时，先写主文档，不先写业务文档。默认一次只写一篇。模块间数据流不写进功能模块文档。

还要修改另一篇正式文档时，列出每一个路径，询问：「是否允许跨模块？」用户回复里同时有「允许跨模块」和这些路径之后，按每篇文档各自的撰写说明更新。回复里没有的路径不改。

## 功能模块主文档

一条主业务时，目录只有这五项，正文按这个顺序写：

- 模块目录结构
- 功能定义
- 核心业务层
- 核心模型
- 核心业务

多条事件业务时，主文档不放时序图。第 4 节标题写「业务文档」，目录链到同目录下的各篇业务文档。

核心业务层只写 ViewModel 的定义、文件路径和方法签名。核心模型只写聚合根、包含的实体和不变条件。类图和用例图不重复同一件事。图中的节点、参与者、箭头只用仓库里的目录名、类名、方法名、字段名。中文写在图外。

## 功能模块业务文档

目录之后只有两部分：

1. 业务定义：这个事件做什么，从哪个操作开始。
2. 时序图：参与者使用主文档里的类名，箭头使用主文档里的方法名。图下用中文按顺序说明。

方法表留在主文档。业务文档点名本次调用的方法。写完后把这篇的链接加进主文档目录。

## 基础应用

目录之后按撰写说明写「功能定义」「使用示例」。有时序图时，下一节标题写「时序」。时序图已经能说明调用顺序时，不画数据流图。图中只用本目录的类名、函数名、方法名。不画功能模块的调用链。

## 项目架构

目录之后只有「项目目录结构」「模块定义」「模块间数据流」。`src/features` 只展开到功能模块目录。功能模块表写 application 用例，不写页面操作，不写 ViewModel。数据流图的节点只使用功能模块目录名。

## 写完后停止

用对应撰写说明逐节核对。缺节、多节、文件名不符、图中出现中文时，先改正这一篇。

然后停止，请用户回复「文档没有问题，业务正常」。用户写出这两句之前，不修改 `src/`。
